# Foundry

## Additional Context

DESIGN.md is the canonical design system for the site. BRAND.md is the identity and voice source of truth (distinct from DESIGN, which is looks, and PRODUCT, which is what/who). PRODUCT.md is the review philosophy and the forever spec: what the audit is, in the present tense. `reference/doc-set-spec.md` is the canonical documentation architecture the suite's skills enforce; `reference/skill-authoring.md` is the standard every SKILL.md follows. `NOTES.md` holds decisions with reasoning, `PROMPTS.md` the phase narrative, `FRICTION.md` the process-friction log. The master plan and phase plans are indexed in TODOS.md's Master Plan block; read them there.

## Project Overview

This repo is a skills suite whose flagship is Production Audit. The unifying thesis: software delivery integrity for people who build products with an AI in the loop, five promises between an idea and its release (intent declared and audited; execution context preserved; the outcome instrumented; docs aligned with reality; readiness audited before real users), with documentation engineered as the agent's memory so a cold start cannot go wrong.

The shape: ten skills under `skills/` (production-audit is the flagship inspector, foundry the pre-ship conductor; frame, scaffold, document, phase-plan, brand-voice, mobile, instrumentation, and readout operationalize the disciplines), the versioned report contract under `schema/`, published audit reports under `reports/`, suite standards under `reference/`, and a Next.js site under `app/` (deployed on Fly as `foundry-skills`, custom domain live) that renders the suite: marketing landing, `/skills` directory, Behind-the-Build hub, and the `/reports` hub. What each skill does lives in its own `skills/<name>/SKILL.md`; read those, not a summary here. The Makefile is the task surface (`install`, `validate`, `sync-bundled`, `sync-version`); site commands are the standard npm scripts in `package.json`.

## Gotchas

- **ESLint:** `eslint.config.mjs` imports `eslint-config-next`'s native flat-config array directly and spreads it. Do NOT wrap it in `FlatCompat`: FlatCompat's schema validator hits a circular-reference bug on the plugin objects and crashes lint.
- **The Dockerfile COPYs runtime-read files explicitly.** The root docs (`PRODUCT/BRAND/DESIGN/NOTES/PROMPTS/FRICTION.md`), `VERSION`, `skills/*/SKILL.md`, and `reports/*.json` are read at runtime via fs, and Next's standalone trace omits fs-read files. A new runtime-read file must be added to the Dockerfile, or it breaks in production only.
- **`SITE_URL` and `SITE_ORIGIN` deliberately disagree.** Site metadata (`SITE_URL` in `app/layout.tsx`: OG, canonical, JSON-LD) points at the intended production domain ahead of DNS, while `fly.toml`'s `SITE_ORIGIN` (the Supabase magic-link redirect target) stays on the fly.dev origin until DNS and the Supabase redirect allowlist move together (TODOS Phase 13 launch tail). "Fixing" the mismatch breaks live auth.
- **The Supabase secret names are deliberately NOT `NEXT_PUBLIC_`** (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `ADMIN_EMAILS`; the gate fails closed if unset). Next inlines `NEXT_PUBLIC_*` at build time and the Docker image builds without secrets, so runtime-set secrets under those names would never be read. Local `/reports` testing needs them in `.env.local` (see `.env.example`) plus `http://localhost:3000/auth/confirm` in the Supabase redirect allowlist.
- **PostHog server capture flushes immediately** (`flushAt: 1, flushInterval: 0`, never awaited in a request path) because Fly machines auto-stop and a buffered event dies with the machine. `NEXT_PUBLIC_POSTHOG_KEY` is needed at BUILD time for the browser bundle, so it lives in `fly.toml [build.args]` (a phc key is public by design); the server reads `POSTHOG_KEY` at runtime. Client and server both no-op when their key env is unset: analytics being down must never break a flow.
- **Identity rule:** the Supabase user id is THE distinct id; pre-auth events key on the normalized email, which `sign_in_completed` aliases to the user id. The one sanctioned exception is `skill_version_check` (below), which keys on the synthetic actor `foundry-suite` because it must carry no identity at all. Never key an event on anything else. The event plan precedes capture code (instrumentation skill discipline): two funnels, suite adoption (anonymous: `$pageview`, `install_copied`, `example_report_viewed`) and reports access (identified: `magic_link_requested`, `sign_in_completed`, `sign_in_failed`, `report_viewed` as activation); plus one out-of-funnel usage event, `skill_version_check` (fires in `/api/version` when an installed skill's rate-limited update check calls in; properties `skill`, `installed_version`, `current_version`; keyed on `foundry-suite` with `$process_person_profile: false`, so it measures check COUNTS, never uniques, no user, install, or IP identity ever attached; captured only for `SKILL_SLUGS` names). It is the narrow exception the instrumentation doctrine defines (skills/instrumentation, "The gate demands a decision"): functional purpose, disclosure as part of the feature, opt-out enforced in the command. Reading it honestly: the stamp file is shared across all skills per `$HOME`, so the `skill` property records the first skill that ran that day, NOT skill popularity, and the denominator is home directories (a devcontainer rebuild or CI runner is a fresh one), roughly active-machine-days per version. A volume spike means the rate limit broke OR someone is hammering the open endpoint; either way the counts are junk for that window, not evidence of growth.

## Source-of-truth rules

- `schema/audit-report.schema.json` is the report contract; the emitting skill (`skills/production-audit/SKILL.md`) and the site's ReportView renderer both conform to it. Changing the schema means updating both in the same commit and bumping `schemaVersion`. A bundled copy ships inside `skills/production-audit/` so installs are self-contained; `make sync-bundled` re-copies it and `make validate` fails on divergence.
- **An install ships only the skill's own directory**, because `make install` symlinks `skills/<name>/`. Anything a SKILL.md tells the agent to read must therefore live inside that directory, never at a repo path like `reference/`, which is not on an adopter's disk. Three bundled copies exist for this reason (the report schema, `brand-voice`'s `BRAND.template.md`, `phase-plan`'s `plan.template.md`); `make sync-bundled` re-copies all three and `make validate` fails on divergence. A skill that must cite a repo-only file (the doc-set spec, the authoring standard) links the raw GitHub URL instead.
- `skills/*/SKILL.md` are the canonical skills. Each user-global copy at `~/.claude/skills/<name>` is a symlink to its `skills/<name>/` directory, never a diverging copy; `make install` recreates any missing symlink.
- **`VERSION` (repo root) is the suite version's single source of truth**, bumped only in the release roll-up commit so main always carries the last released number. The site reads it directly at runtime (`lib/version.ts`, every version shown on a page and served by `/api/version`; the Dockerfile COPYs `VERSION` for exactly this). `make sync-version` stamps it into every SKILL.md frontmatter, every version-check URL, and SECURITY.md's supported-versions line; `make validate` fails on drift in any of them, and on a skills/ directory missing from `SKILL_SLUGS`. Never hand-edit a stamped copy. `package.json`'s version is the site's own concern, deliberately outside this net.
- PRODUCT.md explains why; `skills/production-audit/SKILL.md` instructs how. When the method changes, both change in the same commit.
- `reference/doc-set-spec.md` is the canonical doc architecture; when the doc rules change, they change there first.
- **The public surfaces track every skill, and no skill change merges without them.** Adding, renaming, removing, or materially changing a skill means updating, in the same commit: its `skills/<name>/SKILL.md` (with the `reference/skill-authoring.md` gate), `lib/skills.ts` (`ORDER`, the `USER_INVOKED` classification, and a `SKILL_COPY` entry, or the card renders raw agent-facing prose), the `README.md` skills table, `PRODUCT.md`'s `## The suite` list (it renders publicly at `/behind/product`), and the `CHANGELOG.md` `[Unreleased]` block. `make validate` runs `scripts/check-skill-surfaces.mjs`, which fails the build on a missing entry and on any present-tense "<n> skills" claim that disagrees with the real directory count. Two things the script deliberately cannot judge, so they are yours: whether a `SKILL_COPY` tagline still *describes* the skill after its body changed, and whether the change belongs in the deck's narrative. Nothing derives the count, so every numeral in prose is a hardcoded word; a line whose number is deliberately historical carries a `skills-count-exempt` marker rather than being quietly skipped. The count claims live in `README.md`, `app/page.tsx`, and `app/behind/page.tsx`.
- **The public self-audit tracks the suite.** The published self-audit (`reports/foundry-<date>.json`, `meta.public: true`, rendered at `/example/foundry-<date>`) is the credibility anchor, and because the tool audits itself it is not a static artifact: when the suite changes in a way that alters what an audit of this repo would find (a skill added, removed, or materially changed; a new route, gate, or trust boundary; a dependency or header change), regenerate the self-audit under the current method and replace the published report in the same phase. A self-audit describing a prior version of the suite is the same drift as stale marketing copy.
- **Reports contain vulnerability findings for live products.** They are only ever surfaced behind the sign-in gate, to their owner (`meta.owner`) or an admin; nothing under `reports/` may be linked from or summarized on ungated pages beyond aggregate counts and verdict level. `/reports/[slug]` gates itself (signed-out redirect, non-owner 404); only `meta.public` example reports render ungated at `/example/[slug]`.

## Conventions

- Published reports are named `reports/<project-slug>-<YYYY-MM-DD>.json`. The slug becomes the `/reports/[slug]` URL.
- No em dashes in any authored content, including SKILL.md, docs, site copy, and generated report text.
- One word is banned from all authored content in this repo, in any casing: the common noun for a repeated ceremonial practice, spelled r-i-t-u-a-l (spelled out here so the rule itself never contains a searchable occurrence). Where the concept is needed, write "ceremony", "rite", or "routine" instead. House style rule, applied the same way as the em-dash rule.
- **PROMPTS.md carries no raw verbatim prompt log.** The de-personalization pass before the public flip removed it, because the file may render publicly. Never reintroduce verbatim prompts; record what happened in the Phases narrative instead.
- Doc separation (one owner per fact, reference instead of copy) and the self-maintenance cadence for NOTES.md, PROMPTS.md, and FRICTION.md are owned by `reference/doc-set-spec.md` and the `document` skill. Keep those files current as work happens, per that skill; duplication between docs is drift.

## Commit Workflow Overrides

The maintainer's standard workflow applies: all work on feature branches, commit messages via temp file and `git commit -F`, every unit of work ends in a PR. Project-specific steps:

**Step 2, Build and verify:** `npm run typecheck && npm run lint && npm run build`. For skill or schema changes, also `make validate` (schema-validates the sample and every published report, checks the bundled schema copy, and enforces the cross-field report invariants).

**Step 5, Update CLAUDE.md:** Only for changes to agent-facing gotchas, conventions, or source-of-truth rules. Never copy content from the other docs into here.

**Step 5 (parallel), Update NOTES.md, PROMPTS.md, FRICTION.md:** Per the `document` skill's self-maintenance cadence. If any are out of date, bring them current before staging the commit.

**Step 6, README.md and TODOS.md:** Update per the workspace format specs when counts, descriptions, or backlog items change.
