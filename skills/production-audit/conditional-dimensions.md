# Conditional dimensions

Read when Phase 0 marks a conditional dimension applicable; each entry is that dimension's required artifact for its subagent.

- **operability**: can the team tell the system is healthy and act when it is not? Logs/metrics/traces on the critical flows, a dashboard that exists and has an owner, alerts with a named receiver, SLOs or at least an explicit "what is too slow/too broken", runbooks or failure notes for the known failure modes, and clear ownership. A system nobody can observe fails silently. This dimension audits whether the observability exists and is owned; whether the surface can actually be read and acted on (elevation, windows, a failed read rendering as a zero) is the `readout` skill's discipline, and a filled `readout` artifact is the record to cite where one exists.
- **testing-confidence**: not coverage percentage, but whether the tests would catch the failures this report cares about. Are the critical flows exercised end to end? Do contract/integration tests cover the external seams? Crucially: do tests exercise the specific controls other findings rely on (the authz check, the idempotency guard)? A control this report calls verified-safe that no test pins down is one refactor away from silently vanishing. The model is an external seam: each LLM feature has an eval set that runs on a model or prompt change, and a test pins each agent tool gate, including an injected-content exfiltration case (no live attack). **A control no test can reach is a finding in its own right**, separate from the missing test: a threshold hardcoded in the module that enforces it, a client constructed at import time with no seam to substitute, an allowlist frozen in a module-scope constant. The code may be correct today, and nothing can demonstrate it stays correct, so the finding is on the untestable construction and its remedy is the seam, not the test.
- **data-migration-safety**: migration ordering and reversibility (does the migration run before or after the code that needs it; what happens on rollback), backup existence AND restore path (an untested restore is a hope, not a control), deletion/retention behavior, and recovery from partial or corrupted writes. Also:
  - **Migrations** on a large or hot table are checked for lock-taking DDL and expand/contract sequencing.
  - **Deletion reach:** a user-initiated destructive action is reversible for a stated window or explicitly confirmed. User erasure reaches every table holding the user's data and every egress-map sink, and states how backups are handled. Uploads and generated files in object storage follow a declared retention rule and are not orphaned when their record is deleted. Customer account closure is traced as a flow: provider subscription ended, sessions and API keys revoked, export where declared, deletion per retention. Staff offboarding is outside.
  - **Recovery table:** one row per datastore and environment: the backup, when a restore was last exercised, and the rebuild path (versioned config or written provisioning steps; hand-built state is a finding). Judge it against the release policy's `recovery:` RTO and RPO, and a blank target is a finding. Backup credentials are separate from app credentials and backups are deletion-protected. An erasure log is reapplied after a restore. A region-loss row is judged against the RTO; a second region is required only when the RTO demands it. A restore test is `configuration-confirmed` where a runbook or scheduled job shows it, else `needs-verification`.
- **release-safety**: how a bad version reaches users and how it gets pulled back, and how anyone knows the good version arrived. Rollback path and its speed, feature flags or staged rollout for risky changes, forward/backward compatibility between the deployed version and its data/clients, and whether deploy and release are separable. Where the project declares a staging environment, its env schema, migrations, and build match production (none declared is not a finding). A public API with external consumers has a declared compatibility contract (versioning or deprecation policy), and changed response shapes honor it. Plus two ends of the pipeline that audits routinely skip: **artifact identity** (the artifact that was validated is the artifact that ships; a privileged rebuild between CI and deploy is a second, unproved artifact) and **post-deploy verification** (a named check that exercises the user-visible outcome on the primary surface after deploy; an uploaded artifact or a green workflow is not the user outcome).
- **performance-capacity**: latency budgets on the hot paths, query fan-out (N+1 and unbounded queries on real data volumes), resource cliffs (memory, connections, file handles, quota), and what happens at 10x current load. **Spend is a resource cliff:** each metered dependency (LLM, email, compute) has a loop bound or cap in code and a provider spend alert (alert config is `notAssessed` on a static run), and LLM spend has a per-actor cap enforced in code. **Client budget:** shipped JavaScript and main-thread work per primary route against a stated low-end device budget; real-device numbers are `notAssessed` on a static run. Static review reads the code shape; real latency numbers are runtime evidence.
